## Challenged Songs

Three summary counts: Challenged (unique segment identities), Succeeded (unique segments with a successful full attempt), Full Challenges (count of full attempts). Filters: All, In Progress, Completed, Succeeded. Sort recently played by default. Each card has title/composer/level, aggregate status, Best Completion, Best Accuracy (maximum only among full attempts), attempts count, last played, Details, Challenge/Replay; preserve favorite and preview wherever identity is verified. Only one expanded Details at a time. Status reflects best historical achievement; missing legacy result fields are unknown, not 0 or fabricated. Best Completion is maximum over all known attempts. A success is derived from the same fully completed attempt and existing threshold (>=90%); not a combination of independent maxima.

## Details pagination

- Page size exactly 10; last page may have fewer. Newest attempts first in list, same page plotted oldest to newest (left to right). Page 1 is newest. Use Newer / Older, total count, current page, global attempt numbers; no renumbering on page change. For 26 attempts, pages 1/2/3 list #26–17 / #16–7 / #6–1; chart shows #17–26 / #7–16 / #1–6, respectively.
- Both list and plot come from the exact same 10-row array. No full-history chart while paginating; fixed y range 0–100%, 90% reference, completion solid amber and accuracy dashed green. Partial accuracy is labeled as such in cards/tooltip; missing values remain gaps. Preserve all-time Best Completion/Best Accuracy and personal best when changing history page. Show only one personal-best marker for ties (latest full attempt).
- Change page without navigating away or reflowing entire website; keep focus/scroll near chart and pagination. Reset on new segment or account. Do not truncate Supabase results (default row limits); server pagination for large history: count + ordered range, using ended_at DESC, attempt_id DESC, stable snapshot/cursor for concurrent submissions; separately query lifetime summary. `ChallengeHistoryDetails.tsx` is a small-data view component accepting full deduplicated history; adapt the same presentation to server paging if needed.

## Data boundary (required before production)

Currently `getBestAccuracyPerSong()` in `src/features/challenge-history/api.ts` filters aligned scores; `listChallengeRecordings()` is tied to research recordings and `user_play_logs` is written after Worker validation. Neither is adequate for immediately available product results independent of MIDI upload. Do not falsely present those rows as complete product history. UI phase may use isolated dev fixtures (not shipped). Then implement lightweight authenticated product outcome persistence + local recovery, shared attempt_id, per-segment identity, frontend note accuracy, actual completion, finished/exited, success, difficulty canonical from catalog, scoring version. Persist outcome independently of MIDI existence/upload and Alignment. Update product query and deduplicated local optimistic state. Distinguish full and partial results. Preserve old fields without inventing scores/completion or bypassing privacy boundaries. Research pipeline, KT labels and public leaderboard are not part of this scoped UI change. Any leaderboard metric migration should be a separate explicitly approved change to existing home module only.
